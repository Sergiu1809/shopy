## Approach
Add the database layer with no repositories, services, endpoints or seed.

- **`app/models/`** holds the models, as brief §6 lays out. One `Base` (`DeclarativeBase`)
  carries a `MetaData(naming_convention=…)`, and there are three model modules
  (store, user, catalog).
- **`app/db.py`** has three small functions: `database_url()` reads `DATABASE_URL` and
  raises a clear error when it is unset, `create_engine()` and `create_sessionmaker()`.
  Nothing connects at import time.
- **Alembic** comes from the official async template (`alembic init -t async`), with
  `script_location = %(here)s/migrations`. `env.py` takes the URL only from
  `app.db.database_url()`, so there is no URL in `alembic.ini` (PATTERN-013), and sets
  `target_metadata = Base.metadata`.
- **One revision, `0001`.** It is autogenerated, then reviewed by hand. It runs
  `CREATE EXTENSION IF NOT EXISTS vector` / `unaccent` first and then creates the 11
  tables. Downgrade drops the tables in reverse dependency order and keeps the
  extensions (Q10).
- **Compose:** the `api` service gets
  `command: ["sh", "-c", "alembic upgrade head && exec uvicorn app.main:app --host 0.0.0.0 --port 8000"]`.
  The Dockerfile `CMD` stays as it is, because production migration is P7 (Q-011).
  The worker keeps its own command.
- **Tests run against a real container.** One session-scoped
  `PostgresContainer("pgvector/pgvector:0.8.7-pg16", driver="asyncpg")` starts with
  no init script, so the migration alone has to create the extensions. The fixture
  sets `DATABASE_URL` and runs `alembic upgrade head` once.
  - Schema tests read `information_schema` and `pg_catalog`. They check that the
    columns match exactly, plus types, nullability, identity, defaults, FK delete
    rules, indexes and constraints.
  - Behaviour tests insert rows that should violate each CHECK, UNIQUE and partial
    index and expect the database to reject them. They also delete a parent and
    check that its children are deleted (CASCADE) or that the delete fails (RESTRICT).
  - Migration tests use a second database in the same container: upgrade, downgrade
    base, upgrade again. A drift test compares the models with the database using
    Alembic `compare_metadata` and expects no differences.
- **CI:** no service container (Conflict 2). `ubuntu-latest` has Docker, and the
  existing `uv run pytest` step runs the new tests unchanged.

## Risks
- **Drift-test false positives (A4).**
  - Alembic's comparison of the `lower(email)` expression index, the partial index
    predicate, `server_default` text (`'{}'::jsonb` vs `'{}'`) and `Identity` may
    report differences that are not real.
  - Mitigation: give `server_default`s in the exact form PostgreSQL reflects.
  - If one remains, the builder adds a narrowly scoped `include_object` or
    comparator in the test only, names each excluded object, and covers it in
    `test_schema.py` instead. Never a blanket ignore.
  - The exclusion list goes to the reviewer.
- **Async fixtures and Alembic.** The async `env.py` calls `asyncio.run`, which fails
  inside a running event loop. Alembic commands therefore run only from sync
  fixtures and tests (the session `migrated_url` fixture and the sync round-trip
  test). Engines are created per test function to avoid asyncpg cross-loop errors.
- **mypy strict.** `testcontainers` may lack `py.typed`, which needs a scoped override
  (A7). Alembic's `env.py`/`script.py.mako` need annotations.
- **CI time.** The first pull of the pgvector image takes about 150 MB and adds
  roughly 30–60 s. The backend job's 10 min limit should hold; if it does not, raise
  it to 15.
- **`GENERATED ALWAYS` and seeding.** GH-5 cannot insert explicit IDs without
  `OVERRIDING SYSTEM VALUE`. D-024 says ALWAYS, so GH-5 inserts in a deterministic
  order. This is noted for GH-5, not changed here.
- **The Compose api now needs a rebuild** (`--build`), because there is no bind mount
  for `backend/`. An existing `db-data` volume already has the extensions from the
  init script, and `IF NOT EXISTS` covers that case.

### Considered, not applied
- **psycopg (sync) for Alembic.** A second driver and a second URL scheme. The async
  template with asyncpg uses the URL already in `.env.example`.
- **A GitHub Actions Postgres service.** Conflict 2 chose testcontainers.
- **One container per test module, or a per-test database.** Slow. One container per
  session, plus a fresh database only for the round-trip test.
- **Running the round trip on the main test DB.** It would make other tests depend on
  order. A separate `CREATE DATABASE` isolates it, and it also proves the migration
  works without the init script.
- **Putting `alembic upgrade head` in the Dockerfile `CMD`.** That would decide
  production behaviour, which is P7. The Compose `command` override is local only.
- **A FastAPI `get_session` dependency and a module-level engine.** Nothing uses them
  yet, so GH-4 adds them.
- **Separate FK indexes on `categories.store_id` and `store_policies.store_id`.** Each
  is redundant with the leading column of its composite unique constraint. The
  "every FK leads an index" test enforces the rule either way.
- **`pydantic-settings` for `DATABASE_URL`.** It is one variable; `os.environ` is
  enough today.

### Assumptions
- **A1. Driver.** asyncpg for both the app and Alembic (async `env.py` template). There
  is one URL, `postgresql+asyncpg://…`, as `.env.example` already has.
- **A2. How tests get the DB URL.** The session fixture starts the container, sets
  `os.environ["DATABASE_URL"]` (restored after the session) and calls Alembic
  commands, which read it through `app.db.database_url()`. That is the same path as
  production, with no test-only hooks in `env.py`. The round-trip test points
  `DATABASE_URL` at a fresh database with `monkeypatch`.
- **A3. Test layout.** Flat files in `backend/tests/` (`conftest.py`,
  `test_db_config.py`, `test_schema.py`, `test_constraints.py`, `test_migrations.py`).
  Constraint tests run in a per-test transaction that is rolled back. Async tests use
  `asyncio_mode = "auto"`.
- **A4. Drift test scope.** `compare_metadata` with `compare_type` and
  `compare_server_default`. Any narrowly scoped exclusion is listed in the test and
  in the PR (see Risks). CHECK constraints are proven by behaviour tests, not by the
  drift test.
- **A5. Revision ID.** `0001` (`--rev-id`), so it reads well in logs and in
  `alembic_version`. Later revisions follow `0002`, …
- **A6. Two defaults the gate did not state.** `addresses.is_default DEFAULT false` and
  `products.rating_count DEFAULT 0`. Both stay NOT NULL as Q6 requires. The defaults
  only spare inserts from naming them; GH-5 sets the real values. Say if you want no
  default instead (inserts would then have to set them).
- **A7. mypy override.** Only if `testcontainers` ships without types: an
  `ignore_missing_imports` override scoped to `testcontainers.*`.
- **A8. AGENTS.md §2 is already fixed on disk.** It already lists the real commands
  (GH-1 replaced the "Planned in P0 — not run" block). The copy loaded into this
  session's instructions still showed the old text. The code wins: this PR only adds
  the migration and autogenerate lines and the Docker note, and marks that stale-doc
  item as already done.
- **A9. A new candidate pattern (next PATTERN ID).** "Schema changes: models in `app/models/` + one
  hand-reviewed Alembic revision; text + CHECK for enums; naming convention; every FK
  indexed; the drift test must stay green." Candidates are added freely; promotion is
  your call later.
- **A10. CI.** No workflow step changes. testcontainers uses the runner's Docker. The
  timeout goes up only if the first run shows it is needed.
